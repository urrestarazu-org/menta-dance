**WARNING**:
1. Spec scenario "Authenticated visitor sees the same rendering" (`virtual-course-detail-view`) has no dedicated runtime-covering test with an authenticated session hitting `GET /courses/{courseId}`. The guarantee is structural rather than untested risk — `CourseDetailController.courseDetail(...)` takes no `HttpServletRequest`/token parameter and `GetCourseDetailUseCaseImpl.execute(String)` takes only `courseId`, so there is no code path capable of branching on caller identity — but per this skill's rule that a scenario is compliant only when a covering test passed at runtime, this remains an open gap rather than a rounded-up PASS.
2. Spec scenario "Unknown course or lesson id" (`virtual-lesson-view`) has no full-stack integration test asserting the error view renders for a 404 encountered via the lesson route specifically (only the sibling course-detail route has an integration-level 404 test; the lesson route's 404 mapping is proven only at the adapter-unit level via `VirtualApiAdapterTest`, plus the catalog-404 short-circuit at the use-case level via `GetLessonViewUseCaseImplTest`). The mechanism (`@ResponseStatus`-annotated exception, uncaught, resolving through Spring Boot's default `/error` path) is identical to the proven course-detail case and `LessonViewController` has zero exception handling of its own, so risk is low, but the exact scenario lacks a directly covering runtime test.
3. `tasks.md`'s own task 2.9 narrative ("no production change is needed... the filter's existing `authentication == null` branch... is what actually protects anonymous requests") undersells what was actually shipped: commit `46a80e7` (PR 2, #181) added a genuine production change — an explicit `authentication instanceof AnonymousAuthenticationToken` clause in `TokenRefreshFilter.doFilterInternal` (line 102) — which the filter's own Javadoc and inline comments correctly describe as "defense in depth." This is a documentation/tasks-artifact drift, not a code defect: the shipped security posture is stronger than tasks.md's prose describes, and matches the task brief's own item 4 exactly.
4. `VirtualApiAdapter`'s generic `catch (WebClientResponseException e)` wrapper branches, `mapHttpException`, `parseRetryAfter`'s malformed-header catch, and defensive null-response/null-body guards are not exercised by any test (67% line / 58% branch coverage on this class specifically). This mirrors the same untested-defensive-code shape already present in the precedent `AuthApiAdapter`, so it is not new debt, but it is a real, if pre-existing-pattern, coverage gap on the newly-written class.
