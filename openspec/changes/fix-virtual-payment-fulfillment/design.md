# Design: Virtual Payment Fulfillment Regression Guard

**Change**: `fix-virtual-payment-fulfillment`
**Issue**: #114
**Status**: Ready for implementation
**Scope**: Billing integration regression test only

## Context and Evidence

The defect described by #114 was already corrected in `0bd2182`
(`fix(billing): reorientar fulfillment post-pago (#123)`). The current
`PaymentVerificationService` does not invoke a Virtual push port:

```text
WebhookVerificationWorker.process(RECEIVED row)
  -> PaymentVerificationService.verify(providerPaymentId)
    -> persist Payment.COMPLETED
    -> ensureFulfillment(PaymentTarget.Virtual)
      -> find checkout-created Subscription by payment id
      -> PlanRepository.findById(subscription.planId)
      -> Subscription.activate(confirmedAt, durationDays, plan.courseIds)
      -> Subscription.assigned()
      -> SubscriptionRepository.save(...)
```

`Subscription.activate` is already idempotent: it preserves existing dates and
the frozen course snapshot; `ensureSubscription` repairs an already active
subscription that does not grant access by applying `assigned()` only.

The existing app integration test covers physical webhook fulfillment but has
no virtual-checkout-to-`ACTIVE/ASSIGNED` assertion. That is the remaining
regression gap. This change therefore adds a single end-to-end, persisted-state
test. It does not reimplement the production fulfillment path.

## Decision

Exercise the real Billing checkout use case to create the plan-bound payment
and pending subscription, then inject an approved provider result and execute
the real inbox worker. Assert persisted records through Billing repositories.

This proves the production route rather than duplicating its construction in a
fixture. It remains an application integration test: Mercado Pago is mocked at
the `PaymentProviderPort`, while MySQL, the Billing transaction wrappers,
repositories, webhook worker, and domain model are real.

No Virtual module bean, port, adapter, HTTP call, event, or database table is
involved. The entitlement is the Billing subscription snapshot; #56 owns
Virtual's eventual read-side consumption.

## Test Design

### File under test

`api/app/src/test/java/com/menta/app/integration/billing/PaymentWebhookIntegrationTest.java`

### Additions to the integration fixture

- Autowire `CreateSubscriptionCheckoutUseCase`, `PlanJpaRepository`,
  `SubscriptionJpaRepository`, and `SubscriptionCourseJpaRepository`.
- Mock `PaymentPreferencePort` so the actual checkout succeeds without an
  external provider call.
- Seed one active Billing plan with a deterministic duration and two opaque
  course IDs. Clean its plan/subscription rows after each test, respecting the
  child-first order for course snapshot rows.
- Use the checkout result to obtain the local payment/subscription instead of
  constructing `PaymentJpaEntity` or `SubscriptionJpaEntity` directly.
- Build a `WebhookInboxJpaEntity` for the result's provider payment id, mock a
  matching approved `ProviderPaymentResult`, and call `worker.process(row)`.

### Single regression scenario (AC-1, AC-2, AC-3)

`a_matching_approved_virtual_payment_activates_and_assigns_the_local_subscription`

1. **Given** an active plan with `course-a` and `course-b`, and a successful
   virtual checkout generated by the real use case.
2. **When** its matching approved provider payment is processed through the
   real `WebhookVerificationWorker`.
3. **Then** the persisted payment is `COMPLETED`.
4. **And** the subscription is `ACTIVE` with fulfillment status `ASSIGNED`.
5. **And** its persisted snapshot is exactly `[course-a, course-b]`.
6. **And** no `Purchase` and no `common_outbox_events` row are created. This is
   the observable regression guard against reintroducing the physical/outbox
   path; the compile-time absence of `VirtualAccessGrantPort` makes a direct
   push adapter impossible without a separate production change.

The test must intentionally fail before adding assertions/fixture support only
if the already-integrated production behavior regresses. It should pass with
the current implementation without modifying production sources.

## Failure and Idempotency Boundary

`PaymentVerificationService` already treats a missing local plan as a
fulfillment exception: the payment stays `COMPLETED` and the subscription is
saved as `EXCEPTION`. A completed payment with an active, unassigned
subscription is repaired to `ASSIGNED` without altering dates or snapshots.

Do not add a synthetic database-write-failure test in this change. A persistence
exception currently happens inside the worker's single `REQUIRES_NEW`
transaction; it triggers the established inbox retry/reconciliation behavior,
not a separately committable `Subscription.EXCEPTION` record. Making that
different would require an explicit transactional design change and is not
needed to close the #114 push-placeholder regression. The happy-path test
guards the issue's actual production failure; existing unit tests retain the
local-plan-missing and idempotent recovery behavior.
